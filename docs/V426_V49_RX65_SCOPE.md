# v4.26 — one CC1101 erratum correction atop proven v4.9

Reference: TI CC1101 silicon errata SWRZ020E (https://www.ti.com/lit/swrz020). CC1101 has a 64-byte physical RX FIFO and an extra SPI prefetch byte. In some conditions RXBYTES reports 65 without FIFO overflow; the status error bit is **not** suppressed. Reads stay bounded to 64 bytes per burst, and preserve final incomplete packet byte. Applies exact previously-existing v4.11 patch as single v4.9 extension, without bringing the v4.10 diagnostics or v4.12+ poll changes.

Baseline `experiment/v4.9-stable-marcstate-eof` @ `11b09de7f87ade632453f772c37940dbdb470c94`, 8 original patches unchanged/hashes guarded. 147min 215/216 correctly decoded GAMA350 full frames; after rollback on ESPHome 2026.10.1: 11/11 decoded, Apator 43, zero overflows, zero RXBYTES65 in 8min. Therefore **no demonstrated ability to improve nominal throughput**; aim is error-path robustness. We must NOT promise it will beat v4.9. Two newer variants v4.25/v4.25a failed quickly, and their enlarged Radio object is not changed here.

Code scope: new patch touches ONLY cc1101_fifo.h and transceiver_cc1101.cpp; original IRQ/Radio component.cpp/h, the 200us poll delay, MARCSTATE verification, FIFO16 threshold, 325kHz BW, pin config and settings all unchanged. Native tests guard 65-safe bound and existing 0..64 behavior; CI builds on ESPHome 2026.10.1 via official local upstream and real GitHub external_component, with synthetic credentials; CI never flashes.

Before any OTA ensure all 4 CI results PASS. Supervised hardware test from branch `experiment/v4.26-v49-rxbytes65-only`, same YAML with `refresh: always` and Clean Build Files. Verify BOTH meters and 0 recurring overflow/invalid count in first 2–3min; on failure revert to v4.9 immediately. If safe compare exact 34min against v4.9 (45/45 GAMA 326B decoded, Apator 198, zero overflow, ~32 FIFO bursts); then >147min durability. Check absolute decoded/nominal slots separately from percent of full frames. Branch remains an unmerged experiment, not automatically a production upgrade. Physical runtime can still regress due to compiled-code changes even when Radio object layout unchanged.
